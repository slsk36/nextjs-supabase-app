# PRD — 모임해 (가칭)

> 링크 하나로 만들고, 링크 하나로 응답받는 **일회성 모임 관리 앱**

| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.0 |
| 작성일 | 2026-08-01 |
| 상태 | 초안 (리뷰 대기) |
| 대상 릴리스 | MVP (Phase 1) |

---

## 1. 개요 · 문제 정의

### 1.1 배경

동창회, 집들이, 스터디 뒤풀이 같은 **일회성 소규모 모임**은 대부분 카카오톡 단톡방에서 참석자를 셉니다.
이 방식에는 세 가지 고질적인 문제가 있습니다.

1. **응답 유실** — "저 갈게요"가 다른 대화에 묻혀 스크롤 위로 사라집니다.
2. **집계 부담** — 주최자가 대화를 거슬러 올라가며 손으로 인원을 셉니다.
3. **변경 추적 불가** — 나중에 못 가게 된 사람의 번복이 반영되지 않습니다.

구글 폼·네이버 폼으로 대체할 수는 있지만, 이들은 범용 설문 도구라
"언제 어디서 모이는지"와 "지금 몇 명인지"를 한 화면에서 보여주지 못합니다.

### 1.2 한 줄 정의

> **주최자는 1분 안에 이벤트를 만들어 링크를 공유하고,
> 참석자는 로그인 없이 이름만 입력해 참석 여부를 응답한다.**

### 1.3 차별점

| | 카톡 단톡방 | 구글 폼 | **모임해** |
|---|---|---|---|
| 참석자 진입장벽 | 없음 | 없음 | **없음 (비로그인)** |
| 실시간 인원 집계 | ✕ | △ (스프레드시트) | **○ (전용 대시보드)** |
| 일시·장소 정보 표시 | △ (공지) | ✕ | **○** |
| 응답 번복 반영 | ✕ | △ | **○ (본인 응답 수정)** |

## 2. 타겟 사용자 · 페르소나

### 2.1 주최자 (Host) — 로그인 사용자

> **김지원 / 32세 / 대학 동아리 총무**
> 3년 만의 동창 모임을 준비 중. 단톡방에 인원을 물어봤지만 절반만 답했고,
> 그마저도 누가 답했는지 헷갈립니다. 식당 예약 인원을 확정해야 해서 마음이 급합니다.

- **필요한 것**: 만들자마자 바로 공유할 수 있는 링크, 한눈에 보이는 참석 인원
- **쓰지 않을 것**: 복잡한 설정, 참석자에게 가입을 요구하는 기능

### 2.2 참석자 (Guest) — 비로그인 사용자

> **박서준 / 31세 / 직장인**
> 카톡으로 링크를 받았습니다. 지하철에서 폰으로 열어볼 겁니다.
> 회원가입을 요구하면 그냥 창을 닫고 단톡방에 "갈게요"라고 씁니다.

- **필요한 것**: 링크를 열면 바로 보이는 일시·장소, 3초 안에 끝나는 응답
- **쓰지 않을 것**: 회원가입, 앱 설치

### 2.3 설계에 미친 영향

두 페르소나의 요구가 **"참석자에게 로그인을 요구하지 않는다"** 는 핵심 제약을 만듭니다.
이 결정이 8장의 보안 설계 전체를 좌우합니다.

## 3. 핵심 사용자 시나리오

### 3.1 주최자 여정

```
로그인
  → [이벤트 만들기] 클릭
  → 제목·일시·장소 입력 후 저장
  → 공유 링크 자동 발급 → [링크 복사] 클릭
  → 카톡 단톡방에 붙여넣기
  → (수시로) 대시보드에서 참석 12 / 불참 3 / 미정 5 확인
  → 식당 예약 인원 확정
```

### 3.2 참석자 여정

```
카톡에서 링크 클릭
  → 이벤트 페이지 열림 (로그인 화면 없음)
  → 일시·장소·주최자 확인
  → 이름 입력 + [참석] 선택 → 제출
  → "응답이 저장되었습니다" 확인
  → (며칠 뒤 일정이 생겨) 같은 링크 재방문
  → 이전 응답이 그대로 표시됨 → [불참]으로 변경
```

### 3.3 예외 시나리오

| 상황 | 기대 동작 |
|---|---|
| 존재하지 않는 링크 | 404 페이지 — "이벤트를 찾을 수 없습니다" |
| 주최자가 취소한 이벤트 | 이벤트 정보는 보이되 "취소된 모임입니다" 배너 표시, 응답 폼 비활성화 |
| 이미 지난 이벤트 | 정보는 보이되 응답 폼 비활성화, "종료된 모임입니다" 표시 |
| 주최자가 이벤트 삭제 | 링크 접근 시 404 |

## 4. 범위 (Scope)

### 4.1 In Scope — MVP (Phase 1)

- 이벤트 생성 · 수정 · 삭제 (주최자)
- 추측 불가능한 공개 링크 자동 발급
- 내 이벤트 목록 (예정 / 지난 이벤트)
- 공개 이벤트 페이지 (비로그인 접근)
- 비로그인 참석 응답 (참석 / 불참 / 미정)
- 응답 수정 · 철회
- 응답 현황 집계 및 참석자 명단
- 이벤트 취소 상태 관리

### 4.2 Out of Scope — Phase 2 이후

아래 기능은 **의도적으로 제외**했습니다. MVP의 목표는
"단톡방보다 나은 최소한의 경험"을 빠르게 검증하는 것이며,
아래 기능들은 모두 그 검증 이후에 가치가 생깁니다.

| 제외 기능 | 제외 이유 | 우선순위 |
|---|---|---|
| 정원 제한 · 대기자 | 사적 모임은 정원 초과가 드묾 | Phase 2 – 상 |
| 알림 (이메일 / 카톡) | 외부 연동 비용, 카톡은 발송 사업자 심사 필요 | Phase 2 – 상 |
| QR 체크인 | 현장 운영 기능. 50명 이하 모임엔 과함 | Phase 3 |
| 준비물 · 회비 정산 | 정산은 별도 도메인. 앱 목적이 흐려짐 | Phase 3 |
| 반복 이벤트 | "일회성 모임"이라는 제품 정의와 충돌 | 보류 |
| 댓글 · 방명록 | 단톡방이 이미 그 역할을 함 | 보류 |
| 이미지 업로드 (커버) | Supabase Storage 도입 필요 | Phase 2 – 중 |

## 5. 기능 요구사항

우선순위: **P0** = MVP 필수 / **P1** = MVP 포함하되 후순위

---

### F-01 · 이벤트 생성 — P0

주최자가 새 이벤트를 만든다.

**입력 항목**

| 필드 | 필수 | 제약 |
|---|:---:|---|
| 제목 | ✓ | 1~100자 |
| 설명 | | 0~2000자 |
| 장소 | | 0~200자 |
| 시작 일시 | ✓ | 유효한 날짜/시간 |
| 종료 일시 | | 시작 일시 이후여야 함 |

**수용 기준**
- [ ] 필수 항목 미입력 시 저장 버튼이 동작하지 않고 필드별 에러 메시지가 표시된다
- [ ] 종료 일시가 시작 일시보다 이르면 검증 에러가 표시된다
- [ ] 저장 성공 시 이벤트 관리 페이지로 이동하고 공유 링크가 즉시 보인다
- [ ] 저장 중에는 버튼이 비활성화되어 중복 제출이 불가능하다

---

### F-02 · 이벤트 수정 · 삭제 — P0

주최자 본인만 자신의 이벤트를 수정·삭제할 수 있다.

**수용 기준**
- [ ] 다른 사용자의 이벤트 수정 페이지에 직접 URL로 접근하면 접근이 거부된다 (DB 레벨 차단)
- [ ] 삭제 시 확인 다이얼로그를 거친다
- [ ] 삭제하면 해당 이벤트의 모든 응답도 함께 삭제된다 (`ON DELETE CASCADE`)
- [ ] 삭제 후 공유 링크로 접근하면 404가 표시된다

---

### F-03 · 공개 링크 발급 — P0

이벤트 생성 시 추측 불가능한 공개 링크가 자동 발급된다.

**수용 기준**
- [ ] 이벤트마다 고유한 `public_slug`가 생성된다 (21자 이상 URL-safe 랜덤 문자열)
- [ ] 관리 페이지에 `https://<도메인>/e/<slug>` 전체 URL과 [복사] 버튼이 있다
- [ ] 복사 성공 시 토스트로 피드백한다
- [ ] slug는 이벤트 수정 시에도 변경되지 않는다 (이미 공유된 링크가 깨지면 안 됨)

> **설계 의도** — slug 자체가 접근 권한입니다(capability URL). 순번 ID를 쓰면
> `/e/1`, `/e/2`로 남의 모임을 훑어볼 수 있으므로 반드시 랜덤이어야 합니다.

---

### F-04 · 내 이벤트 목록 — P0

로그인 사용자가 자신이 만든 이벤트를 확인한다.

**수용 기준**
- [ ] **예정** / **지난 이벤트** 탭으로 구분된다 (기준: `starts_at` vs 현재 시각)
- [ ] 각 카드에 제목, 일시, 장소, 참석 인원 수가 표시된다
- [ ] 예정 이벤트는 가까운 순, 지난 이벤트는 최근 순으로 정렬된다
- [ ] 이벤트가 하나도 없으면 빈 상태 안내와 [이벤트 만들기] 버튼이 표시된다

---

### F-05 · 공개 이벤트 페이지 — P0

비로그인 사용자가 공유 링크로 이벤트 정보를 확인한다.

**수용 기준**
- [ ] 로그인하지 않은 상태에서 `/e/<slug>` 접근이 가능하다 (**리디렉트되지 않는다**)
- [ ] 제목, 설명, 일시, 장소, 주최자 이름이 표시된다
- [ ] 현재 참석 인원 수가 표시된다
- [ ] 모바일 화면에 최적화되어 있다 (참석자 대부분이 모바일로 접속)
- [ ] 존재하지 않는 slug는 404를 반환한다

---

### F-06 · 비로그인 참석 응답 — P0

링크를 받은 사람이 로그인 없이 참석 여부를 응답한다.

**입력 항목**

| 필드 | 필수 | 제약 |
|---|:---:|---|
| 이름 | ✓ | 1~50자 |
| 참석 상태 | ✓ | `참석` / `불참` / `미정` 중 하나 |
| 한마디 | | 0~200자 |

**수용 기준**
- [ ] 회원가입·로그인 없이 응답이 저장된다
- [ ] 이름 미입력 시 검증 에러가 표시된다
- [ ] 제출 성공 시 폼이 "응답 완료" 상태로 바뀌고 [수정] 버튼이 나타난다
- [ ] 취소된 이벤트 / 종료된 이벤트에서는 폼이 비활성화된다

---

### F-07 · 응답 수정 · 철회 — P0

응답한 사람이 같은 링크로 재방문했을 때 자신의 응답을 고칠 수 있다.

**동작 방식**
1. 최초 응답 시 서버가 임의의 `edit_token`을 생성해 응답 레코드에 저장한다
2. 같은 값을 **HttpOnly 쿠키**로 브라우저에 내려준다 (키: `rsvp_<slug>`, 유효기간 90일)
3. 재방문 시 쿠키의 토큰으로 기존 응답을 조회해 폼에 채운다
4. 수정·철회 시 토큰이 일치해야만 반영된다

**수용 기준**
- [ ] 응답 후 재방문하면 이전 응답이 폼에 채워져 있다
- [ ] 상태를 바꿔 다시 제출하면 새 레코드가 생기지 않고 기존 레코드가 갱신된다
- [ ] [응답 철회]로 자신의 응답을 삭제할 수 있다
- [ ] 다른 브라우저·시크릿 모드에서는 새 응답으로 취급된다 *(알려진 한계 — 9.4 참고)*

---

### F-08 · 응답 현황 집계 · 명단 — P0

**수용 기준**
- [ ] 이벤트 페이지와 관리 대시보드 모두에 `참석 N / 불참 N / 미정 N`이 표시된다
- [ ] 명단은 상태별로 그룹화되어 이름과 한마디가 표시된다
- [ ] 관리 대시보드에서는 응답 시각도 함께 표시된다
- [ ] 응답이 없으면 "아직 응답이 없습니다" 안내가 표시된다

---

### F-09 · 이벤트 취소 — P1

**수용 기준**
- [ ] 관리 대시보드에서 [모임 취소]로 상태를 `cancelled`로 바꿀 수 있다
- [ ] 취소된 이벤트의 공개 페이지 상단에 취소 배너가 표시된다
- [ ] 취소 상태에서 응답 폼이 비활성화된다
- [ ] 취소를 되돌릴 수 있다 (`published`로 복귀)

> 삭제와 취소를 분리하는 이유: 이미 링크를 받은 사람이 404를 보면
> "잘못된 링크인가?" 하고 혼란스러워합니다. 취소는 **사실을 전달**해야 합니다.

---

### F-10 · 로그인 사용자 응답 연결 — P1

**수용 기준**
- [ ] 로그인 상태로 응답하면 `rsvps.user_id`에 사용자 ID가 저장된다
- [ ] 이름 필드에 프로필 이름이 기본값으로 채워진다
- [ ] 로그인 사용자는 쿠키가 없어도(다른 기기여도) 자신의 응답을 수정할 수 있다

## 6. 화면 · 라우트 설계

| 라우트 | 접근 권한 | 설명 | 관련 요구사항 |
|---|---|---|---|
| `/` | 공개 | 랜딩 페이지 (스타터 `hero.tsx` 교체) | — |
| `/auth/login`, `/auth/sign-up` | 공개 | 기존 인증 화면 (구현 완료) | — |
| `/events` | 인증 필요 | 내 이벤트 목록 | F-04 |
| `/events/new` | 인증 필요 | 이벤트 생성 폼 | F-01 |
| `/events/[id]` | **주최자 본인** | 관리 대시보드 — 링크 공유, 응답 현황, 명단 | F-03, F-08, F-09 |
| `/events/[id]/edit` | **주최자 본인** | 이벤트 수정 · 삭제 | F-02 |
| `/e/[slug]` | **완전 공개** | 참석자용 이벤트 페이지 + 응답 폼 | F-05, F-06, F-07 |

### 6.1 라우트 네이밍 의도

관리용은 `/events/<uuid>`, 공유용은 `/e/<slug>`로 **경로를 분리**합니다.
같은 경로에 두 종류의 접근 권한을 섞으면 인증 예외 처리가 복잡해지고,
공유 링크도 짧을수록 카톡에서 보기 좋습니다.

### 6.2 필요한 shadcn/ui 컴포넌트

이미 있음: `button`, `card`, `input`, `label`, `badge`, `checkbox`, `dropdown-menu`

추가 필요:

```bash
npx shadcn@latest add textarea select dialog tabs sonner separator avatar skeleton
```

```
    │ N
┌───┴──────────────┐
│  events          │  ★ 신규
│  - public_slug   │
└────────┬─────────┘
         │ 1
         │
         │ N
┌────────┴─────────┐
│  rsvps           │  ★ 신규
└──────────────────┘
```

### 7.2 `events`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | `uuid` | PK, `default gen_random_uuid()` | |
| `owner_id` | `uuid` | NOT NULL, FK → `auth.users(id)` ON DELETE CASCADE | 주최자 |
| `title` | `text` | NOT NULL, CHECK `length between 1 and 100` | 제목 |
| `description` | `text` | NULL 허용, CHECK `length <= 2000` | 설명 |
| `location` | `text` | NULL 허용, CHECK `length <= 200` | 장소 |
| `starts_at` | `timestamptz` | NOT NULL | 시작 일시 |
| `ends_at` | `timestamptz` | NULL 허용, CHECK `ends_at > starts_at` | 종료 일시 |
| `public_slug` | `text` | NOT NULL, **UNIQUE** | 공유 링크 식별자 |
| `status` | `text` | NOT NULL, default `'published'`, CHECK `in ('published','cancelled')` | 상태 |
| `created_at` | `timestamptz` | NOT NULL, default `now()` | |
| `updated_at` | `timestamptz` | NOT NULL, default `now()` | 트리거로 자동 갱신 |

**인덱스**
- `public_slug` — UNIQUE 인덱스 (공개 페이지 조회의 핵심 경로)
- `(owner_id, starts_at desc)` — 내 이벤트 목록 정렬용

### 7.3 `rsvps`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | `uuid` | PK, `default gen_random_uuid()` | |
| `event_id` | `uuid` | NOT NULL, FK → `events(id)` **ON DELETE CASCADE** | |
| `user_id` | `uuid` | NULL 허용, FK → `auth.users(id)` ON DELETE SET NULL | 로그인 응답자만 |
| `guest_name` | `text` | NOT NULL, CHECK `length between 1 and 50` | 표시 이름 |
| `status` | `text` | NOT NULL, CHECK `in ('going','not_going','maybe')` | 참석 상태 |
| `message` | `text` | NULL 허용, CHECK `length <= 200` | 한마디 |
| `edit_token` | `text` | NOT NULL | 비로그인 본인 확인용 |
| `created_at` | `timestamptz` | NOT NULL, default `now()` | |
| `updated_at` | `timestamptz` | NOT NULL, default `now()` | |

**인덱스 · 제약**
- `(event_id)` — 명단 조회용
- `(event_id, user_id)` — UNIQUE (단, `user_id IS NOT NULL`인 경우만 — 부분 인덱스). 로그인 사용자의 중복 응답 방지
- `(event_id, edit_token)` — UNIQUE. 토큰으로 응답을 찾는 경로

### 7.4 상태 값에 enum 대신 `text` + CHECK를 쓰는 이유

Postgres `enum` 타입은 값 추가·변경 시 마이그레이션이 번거롭습니다.
MVP 이후 `waitlisted` 같은 상태가 추가될 가능성이 있으므로
`text` + `CHECK` 제약이 더 유연합니다. TypeScript 쪽 타입 안전성은
`database.types.ts`가 아닌 **Zod 스키마**로 확보합니다.

### 7.5 `updated_at` 자동 갱신

두 테이블 모두 `BEFORE UPDATE` 트리거로 `updated_at`을 갱신합니다.
애플리케이션 코드에서 매번 세팅하면 빠뜨리기 쉽습니다.

## 8. 보안 · RLS 설계

> **이 문서에서 가장 중요한 섹션입니다.**
> "비로그인 응답 허용"이라는 제품 결정이 만들어내는 유일한 어려운 문제입니다.

### 8.1 문제

RLS로 표현해야 하는 규칙은 이렇습니다.

> *"링크(slug)를 아는 사람만 그 이벤트를 읽고, 그 이벤트에 응답할 수 있다."*

그런데 `anon` 역할에게 `events` 테이블 SELECT를 허용하면
`select * from events`로 **전체 이벤트 목록이 덤프**됩니다.
"slug를 안다"는 조건은 WHERE 절에 불과하지, 권한 경계가 되지 못합니다.

### 8.2 채택 방안 — `SECURITY DEFINER` RPC 함수

`anon` 역할은 테이블에 **직접 접근하지 못하게** 하고,
slug를 인자로 받는 함수만 노출합니다. 함수는 정의자(소유자) 권한으로 실행되므로
RLS를 통과하되, **호출자는 slug를 모르면 아무것도 얻지 못합니다.**

```
[비로그인 참석자]  --slug--> RPC 함수 (SECURITY DEFINER) --> events / rsvps
[로그인 주최자]    ----------> 일반 RLS 정책 -------------> events / rsvps
```

### 8.3 노출할 RPC 함수

| 함수 | 인자 | 반환 | `anon` EXECUTE |
|---|---|---|---|
| `get_event_by_slug` | `p_slug text`, `p_edit_token text` | 이벤트 정보 + 상태별 집계 + 명단 + 내 기존 응답 | ✓ |
| `upsert_rsvp_by_slug` | `p_slug`, `p_name`, `p_status`, `p_message`, `p_edit_token` | 저장된 응답 (+ 신규 발급 토큰) | ✓ |
| `delete_rsvp_by_slug` | `p_slug`, `p_edit_token` | 삭제 여부 | ✓ |

**함수 구현 시 필수 사항**

- `SECURITY DEFINER` + `SET search_path = public, pg_temp`
  → `search_path` 고정을 빠뜨리면 권한 상승 공격에 노출됩니다. Supabase advisor도 이를 경고합니다.
- `get_event_by_slug`는 `owner_id`, `edit_token` 등 **내부 값을 반환하지 않습니다**
- 취소·종료된 이벤트에서는 `upsert_rsvp_by_slug`가 에러를 반환합니다 (프론트 검증만 믿지 않음)
- `p_edit_token`이 주어졌는데 일치하는 응답이 없으면, 조용히 **신규 응답으로 처리**합니다 (토큰 존재 여부를 알려주지 않음)

### 8.4 테이블 RLS 정책

두 테이블 모두 `ENABLE ROW LEVEL SECURITY`. 정책이 없으면 기본 거부입니다.

**`events`**

| 정책 | 대상 역할 | 동작 | 조건 |
|---|---|---|---|
| `events_select_own` | `authenticated` | SELECT | `owner_id = auth.uid()` |
| `events_insert_own` | `authenticated` | INSERT | `owner_id = auth.uid()` (WITH CHECK) |
| `events_update_own` | `authenticated` | UPDATE | `owner_id = auth.uid()` |
| `events_delete_own` | `authenticated` | DELETE | `owner_id = auth.uid()` |
| — | `anon` | — | **정책 없음 = 전면 차단** |

**`rsvps`**

| 정책 | 대상 역할 | 동작 | 조건 |
|---|---|---|---|
| `rsvps_select_as_host` | `authenticated` | SELECT | 해당 `event_id`의 이벤트가 내 소유 |
| `rsvps_all_as_self` | `authenticated` | ALL | `user_id = auth.uid()` |
| — | `anon` | — | **정책 없음 = 전면 차단** |

### 8.5 `public_slug` 생성 규칙

- **21자 이상**의 URL-safe 랜덤 문자열 (nanoid 기본 길이 기준, 약 126비트 엔트로피)
- 생성 위치: **DB 기본값**으로 처리 (`encode(gen_random_bytes(16), 'base64')`를 URL-safe로 치환)
  → 애플리케이션에서 생성하면 클라이언트마다 구현이 갈릴 수 있습니다
- 이벤트 수정 시 변경되지 않습니다 (F-03)

### 8.6 알려진 리스크와 수용 근거

| 리스크 | 영향 | 대응 |
|---|---|---|
| 링크가 유출되면 누구나 응답 가능 | 사적 모임에 모르는 사람이 응답 | **수용.** 카톡 링크 공유가 곧 이 모델. 주최자가 명단에서 이상한 응답을 삭제할 수 있게 함 (Phase 2) |
| 쿠키 삭제 시 응답 수정 불가 | 사용자가 중복 응답 생성 | **수용.** 주최자가 중복을 정리 가능. 로그인 사용자는 F-10으로 해결 |
| 이름만으로 사칭 가능 | 남의 이름으로 응답 | **수용.** 사적 모임 신뢰 모델. 인증을 요구하면 제품 전제가 무너짐 |
| RPC 무차별 호출 | slug 추측 시도 | Supabase 기본 rate limit + 126비트 엔트로피로 사실상 불가능 |

## 9. 기술 아키텍처 · 제약사항

> 이 저장소 고유의 함정입니다. 구현 전에 반드시 읽으세요.

### 9.1 ⚠️ `proxy.ts` 수정이 필수입니다

현재 `lib/supabase/proxy.ts`의 리디렉트 조건은 다음과 같습니다.

```ts
if (
  request.nextUrl.pathname !== "/" &&
  !user &&
  !request.nextUrl.pathname.startsWith("/login") &&
  !request.nextUrl.pathname.startsWith("/auth")
) {
  // → /auth/login 으로 리디렉트
}
```

즉 **`/`와 `/auth/*`를 제외한 모든 경로가 로그인 필수**입니다.
이 상태로는 `/e/<slug>`가 로그인 화면으로 튕겨나가 **F-05·F-06이 아예 동작하지 않습니다.**

구현 시 이 조건에 `/e` 경로 예외를 추가해야 합니다.
(Next.js 16에서는 `middleware.ts`가 아니라 루트의 **`proxy.ts`** 가 그 역할을 합니다.
`middleware.ts`를 새로 만들면 충돌합니다.)

### 9.2 ⚠️ `cacheComponents: true` — 빌드에서만 잡히는 오류

`next.config.ts`에 `cacheComponents: true`가 켜져 있어,
`cookies()`·`headers()`·캐시되지 않은 Supabase 조회는 **반드시 `<Suspense>` 경계 안**에 있어야 합니다.
위반하면 `npm run dev`는 통과하고 **`npm run build`에서만 실패**합니다.

기존 패턴은 `app/protected/page.tsx`를 참고하세요 —
데이터를 읽는 부분을 별도 `async` 컴포넌트로 분리하고 `<Suspense>`로 감쌉니다.

이 프로젝트에서 특히 주의할 지점:
- `/e/[slug]` — 쿠키(`edit_token`)를 읽으므로 해당 부분을 반드시 분리
- `/events` — 목록 조회 부분 분리

### 9.3 Supabase 클라이언트 3종 — 이름이 전부 `createClient`

| 파일 | 용도 | 호출 |
|---|---|---|
| `lib/supabase/client.ts` | `"use client"` 컴포넌트 | `createClient()` — 동기 |
| `lib/supabase/server.ts` | 서버 컴포넌트 / 라우트 핸들러 / 서버 액션 | **`await createClient()`** — 비동기 |
| `lib/supabase/proxy.ts` | `proxy.ts` 세션 갱신 | `updateSession(request)` |

- 서버 클라이언트를 전역 변수에 저장하지 마세요 (Fluid compute)
- 인증 확인은 `getUser()`가 아니라 **`getClaims()`** 를 씁니다 (기존 코드와 통일)

### 9.4 쿠키 정책 (F-07)

| 항목 | 값 |
|---|---|
| 이름 | `rsvp_<slug>` |
| 값 | `edit_token` |
| 옵션 | `httpOnly`, `secure`(프로덕션), `sameSite: "lax"`, `path: /e/<slug>`, `maxAge: 90일` |

`httpOnly`이므로 클라이언트 JS로 읽을 수 없고, **서버 컴포넌트/서버 액션에서만** 접근합니다.
이 때문에 RSVP 폼 초기값은 서버에서 채워 내려야 합니다 (→ 9.2의 Suspense 이슈와 연결).

### 9.5 폼 · 상태 관리

- **React Hook Form + Zod v4 + `@hookform/resolvers`** (모두 설치되어 있음)
- Zod 스키마는 `lib/validations/event.ts`, `lib/validations/rsvp.ts`에 두고
  **클라이언트 검증과 서버 액션 검증에서 함께 재사용**합니다
- 기존 auth 폼(`components/login-form.tsx` 등)은 raw `useState`입니다. **참고하지 마세요.**
- Zustand는 MVP에서 필요 없습니다. 서버 상태는 서버 컴포넌트로, 폼 상태는 RHF로 충분합니다

### 9.6 스키마 변경 · 타입 생성 절차

로컬 Supabase CLI나 마이그레이션 파일이 없습니다. 순서는 다음과 같습니다.

## 10. 비기능 요구사항

### 10.1 반응형 · 모바일 우선

참석자의 절대다수가 **카톡 링크를 통한 모바일 접속**입니다.
`/e/[slug]`는 모바일 레이아웃을 먼저 설계하고 데스크톱으로 확장합니다.

### 10.2 에러 핸들링

| 상황 | 처리 |
|---|---|
| 존재하지 않는 slug / 삭제된 이벤트 | `notFound()` → 404 페이지 |
| 권한 없는 이벤트 관리 페이지 접근 | RLS가 빈 결과 반환 → `notFound()` |
| RPC 호출 실패 | 폼 상단에 에러 메시지, 입력값 유지 |
| 네트워크 오류 | 토스트(`sonner`)로 안내 + 재시도 가능 |

### 10.3 접근성

- 모든 폼 입력에 `<Label htmlFor>` 연결
- 참석 상태 선택은 키보드로 조작 가능
- 에러 메시지를 `aria-describedby`로 입력 필드와 연결

### 10.4 코드 품질

- **`any` 타입 금지**
- DB 타입은 `@/database.types`의 `Tables<"events">` 등을 사용
- 파일명 kebab-case, 컴포넌트 named export, 큰따옴표, 세미콜론, 2칸 들여쓰기
- 컴포넌트는 재사용 단위로 분리 (예: `event-card`, `rsvp-status-badge`, `rsvp-summary`)

- 이벤트 생성 → 링크 복사까지 걸린 시간 (목표: 60초 이내)
- 링크 방문자 대비 응답률 (목표: 70% 이상)
- 응답 수정 발생 비율 (F-07의 가치 검증)

---

## 부록 A · 용어

| 용어 | 정의 |
|---|---|
| **이벤트 (Event)** | 주최자가 만든 일회성 모임 |
| **주최자 (Host)** | 이벤트를 만든 로그인 사용자 |
| **참석자 (Guest)** | 공유 링크로 응답하는 사람. 로그인 여부 무관 |
| **RSVP** | 참석 여부 응답 (프랑스어 *Répondez s'il vous plaît*) |
| **slug** | 공유 링크에 쓰이는 추측 불가능한 랜덤 식별자 |
| **capability URL** | URL을 아는 것 자체가 접근 권한이 되는 설계 |
